# Podcast Artist 创作工具构想

日期：2026-06-02

## 一句话

Podcast Artist 是一个本地优先的播客创作工具。它不是单纯的音频剪辑软件，而是把“录音前的文字素材处理”和“录音后的轻量音频剪辑”放进同一条工作流里，服务于用 AI 辅助准备、录制、整理播客的创作者。

## 核心判断

传统播客工具通常从音频文件开始，但实际创作往往更早开始：选题、资料、提纲、文字稿、事实核查、录音计划，都会直接影响后面的录音和剪辑效率。

最近的实践说明，基础文字稿或大纲在 AI 辅助下处理效率很高。因此可以围绕这种新流程设计一个工具：先处理原始文字素材，再录音，再进入轻量音频剪辑。

## 目标用户

- 独立播客创作者。
- 小团队播客制作人。
- 对剪辑要求不高，但希望快速产出清晰节目草稿的人。
- 需要在录音前反复整理资料、检查说法、补充事实依据的人。

## 整体流程

1. 创建一期节目项目。
2. 在录音前处理文字素材：大纲、基础文字稿、参考资料、待核查问题。
3. 通过 AI/agent 发起资料查询、事实核查、段落改写、补充素材等任务。
4. 根据整理后的稿件去录音。
5. 导入录音素材，进行剪辑。
6. 使用转写结果辅助删除静音、口误、口癖或无效段落。
7. 对简单节目直接导出成品；对复杂节目分轨或整体导出到专业剪辑工具继续处理。

## 录音前：原始素材处理

这一部分是工具最特殊的地方。它不只是一个文档编辑器，而是一个面向播客录制准备的素材处理工作台。

### 基本文稿区

中间区域是一段正在处理的文稿，可以是：

- 完整基础文字稿。
- 简化版大纲。
- 分段讲稿。
- 录音提示词。
- 夹杂资料链接、批注和待处理问题的草稿。

用户的主要阅读、修改和组织动作都发生在这里。

### 资料补充区

右侧是资料补充区，用来承载：

- AI 查到的资料。
- 外部链接、引用、出处。
- 事实核查结果。
- 可插入到文稿中的补充段落。
- 对某个说法的风险提示或替代表达。

资料补充区应该和当前文稿段落有清晰关系，避免补充资料散落成纯聊天记录。

### AI 对话与 agent 任务

AI 对话的位置暂时未定，可以先假设在左侧。关键不是聊天框本身，而是它默认能理解用户当前看到的上下文。

理想状态：

- AI 能知道当前屏幕显示了哪一段文稿。
- AI 能知道用户选中了哪一段、光标在哪一段、正在查看哪些资料。
- 用户可以很自然地说：“这里我想引入一个资料”“这里的说法帮我查一下对不对”“这段能不能补一个更具体的例子”。
- 这类请求会变成持续性的 agent 任务，而不是一次性问答。

### 多任务并行

一个项目文件里应该能同时发起多个 agent 任务。

原因是创作者会反复阅读、反复提出问题。如果用户每提出一个任务都必须等它返回，整个流程会很低效。

需要支持：

- 多个任务同时运行。
- 每个任务绑定到具体段落或资料位置。
- 任务有状态：排队中、运行中、需要确认、已完成、已取消。
- 任务结果可以被采纳、忽略、重新查询或插入文稿。

### 成本与模型配置

工具应该尽量支持性价比高的 AI 使用方式，而不是强绑定某个官方云服务。

可能方向：

- 支持用户自带 API key。
- 支持兼容 OpenAI API 格式的模型服务。
- 支持类似 ACP 这样的 agent/工具协议。
- 后续可考虑接入本地模型或本地工具链。

这里的重点是：模型能力应该是可配置的，创作者可以根据预算和效果自行选择。

## 录音后：轻量音频剪辑

音频剪辑部分的定位要明确：它不是全能 DAW，也不是专业后期软件的替代品，而是处理播客音频草稿、简单节目的轻量剪辑工具。

### 核心能力

- 支持多个音频轨道。
- 默认使用波纹剪辑：删除一段内容后，后面的内容自动吸附到前面，不留下空隙。
- 默认不保留空白；如果需要停顿，用户主动插入空白。
- 支持基础音频标准化。
- 支持基础降噪。
- 支持基础淡入淡出/单入单出能力，这个表述后续需要再确认具体含义。
- 支持整体导出。
- 支持分轨导出，方便进入专业剪辑工具继续处理。

### 转写辅助剪辑

工具应支持文稿识别和转写，让用户可以通过文字快速定位音频问题。

重点场景：

- 快速删除静音段落。
- 快速删除口误。
- 快速删除口癖或重复表达。
- 通过转写文本定位某一段音频。
- 文本和音频时间线联动。

## 产品边界

### 要做

- 播客录音前的稿件和资料处理。
- AI 辅助资料补充、事实核查、改写和任务管理。
- 本地项目文件管理。
- 播客剪辑所需的多轨、波纹剪辑、降噪、标准化、转写和导出。

### 暂时不做

- 云端协作。
- 官方托管模型服务。
- 专业级混音和母带处理。
- 复杂音频插件生态。
- 视频剪辑。
- 面向音乐制作的 DAW 能力。

## 技术方向

初步倾向：

- Electron 技术栈。
- 前端技术实现主要交互。
- 数据库存储在本地。
- 不做云端服务。
- 项目文件和素材尽量保持可迁移、可备份。

本地数据至少需要覆盖：

- 项目基本信息。
- 文稿内容和段落结构。
- 资料补充记录。
- agent 任务列表和结果。
- 音频素材索引。
- 转写文本和时间戳。
- 剪辑决策数据。
- 导出配置。

## 初步信息架构

一个项目可以理解为一期节目。

项目里包含：

- 文稿：大纲、讲稿、录音提示。
- 资料：链接、摘录、核查结果、补充文本。
- 任务：AI/agent 发起的查询、核实、改写、整理任务。
- 音频：录音素材、多轨时间线、剪辑片段。
- 转写：音频识别文本、时间戳、可删除候选段。
- 导出：整体导出、分轨导出、给专业工具继续处理的中间产物。

## 可以作为 MVP 的版本

第一版可以先聚焦一条最短闭环：

1. 创建项目。
2. 编写或粘贴大纲/基础文字稿。
3. 对指定段落发起 AI 资料补充或事实核查任务。
4. 把任务结果插入资料区或文稿。
5. 导入录音音频。
6. 自动转写。
7. 通过文字选择删除对应音频片段。
8. 做基础波纹剪辑、标准化和导出。

这条闭环能够验证最关键的判断：播客工具应该从“录音前的文字素材处理”开始，而不只是从音频时间线开始。

## 待确认问题

- AI 对话区放在左侧是否合适，还是应该做成可浮动/可收起的任务面板？
- 文稿和资料之间是强绑定到段落，还是允许更自由的资料库？
- agent 任务结果是更像聊天消息、资料卡片，还是可追踪的任务单？
- “单入单出”具体指淡入淡出、单声道输入输出，还是另一类音频处理能力？
- 本地项目文件应该是单文件、文件夹结构，还是 SQLite 数据库加素材目录？
- 第一版是否需要直接录音，还是只支持导入录音文件？
- 转写能力优先使用本地模型，还是先接入用户配置的云端 API？

## 当前关键词

# Podcast Artist PRD 草案

版本：0.3
日期：2026-06-02
状态：草案

## 1. 产品定位

Podcast Artist 是一个本地优先的播客创作工具，服务从录音前准备到录音后草剪的完整前期流程。

它的核心不是替代专业 DAW，也不是做一个通用 AI 写作工具，而是把播客创作者已经在做的两件事合并成一个连续工作台：

- 录音前：整理大纲、基础文字稿、资料、待核查问题，并借助 AI/agent 持续补充资料。
- 录音后：导入录音，通过波形和时间线做轻量剪辑，快速得到可发布或可继续精修的音频草稿。转写、降噪和在线服务作为可配置能力预留，不作为第一阶段必须完成的功能。

第一版要验证的核心假设是：播客创作工具应该从文稿和资料处理开始，而不是只从音频时间线开始。

项目定位上，Podcast Artist 应作为开源、本地、可自配置的创作工具，而不是一个绑定官网云服务的 SaaS 客户端。AI、转写、资料检索、降噪等外部能力都通过 provider 配置接入；产品本身不默认提供官方托管服务。

## 2. 目标用户

### 主要用户

独立播客创作者或小团队制作人。他们通常自己完成选题、资料整理、录音、粗剪和发布，愿意使用 AI 提高准备效率，但不希望工作流被云服务和复杂专业软件绑住。

### 典型场景

- 录制前有一个初稿或大纲，需要反复补资料、查事实、改表达。
- 节目录完后，只需要删除明显口误、长静音、重复段落和口癖。
- 简单节目希望直接导出成品。
- 复杂节目希望导出分轨或整体音频，再进入专业工具继续处理。

## 3. 用户痛点

### 文稿准备和音频剪辑割裂

播客准备阶段通常发生在文档、网页、聊天工具和 AI 对话里；剪辑阶段又进入完全不同的音频软件。资料、稿件、核查结果和最终音频之间没有稳定关系。

### AI 对话不理解创作现场

普通 AI 对话需要用户反复复制上下文。创作者正在看的段落、选中的文字、右侧资料、当前录音计划，都不能自然进入 AI 任务。

### 一问一答的 AI 模式不适合创作

播客准备是连续阅读和连续发现问题的过程。用户可能在同一份稿件里同时发起多个查询、核查和改写任务。如果必须等一个任务完成才能问下一个，效率很低。

### 专业音频工具过重

对很多播客来说，粗剪需要的是多轨、波纹剪辑、转写辅助、降噪、标准化和导出，而不是完整 DAW 的复杂能力。

## 4. 产品原则

- 本地优先：项目数据、素材和剪辑决策默认存储在本机。
- 透明可解释：重要数据应该以用户可以理解和追溯的本地文件存在，不能只藏在数据库或运行时状态里。
- 手动可管理：目录结构、文件命名和数据分层要从用户容易翻找、备份、迁移、修复的角度设计，而不是从隐藏数据或保密数据的角度设计。
- 模块解耦：文档、素材库、转写、剪辑、任务账本和导出模块通过清晰的文件与 id 引用协作，避免为了内部方便做成复杂私有大格式。
- 工作流连续：文稿、资料、任务、音频和转写结果属于同一个节目项目。
- 素材稳定副本：用户导入的音频和附件要复制进本地素材库，文档、转写和剪辑都引用素材库资产，而不是直接依赖用户原始路径。
- 开源和自配置服务：项目默认不提供官网服务，模型、转写、资料检索、降噪等能力都由用户或开发者配置 provider。
- AI 可替换：模型和 agent 能力可配置，不强绑定任何单一服务。
- 轻量剪辑：音频能力只覆盖播客草剪，不扩展成专业 DAW。
- 默认高效：默认波纹剪辑，删除内容后自动吸附，不制造无意空白。
- 非破坏性编辑：素材库中的音频资产永不改写，文档写入前自动保留旧版本快照。
- 并行思考，串行落笔：AI/agent 任务可以并行运行，但写入同一份文稿或同一份剪辑计划时必须经过统一队列。
- 结果可迁移：简单节目直接导出，复杂节目能交给专业工具继续处理。

## 5. 产品切入方式

### 推荐：文稿工作台 + 轻量音频草剪

第一版同时覆盖录音前和录音后，但功能都保持克制。文稿侧验证 AI/agent 任务，音频侧验证导入、proxy/peaks、基础时间线、波纹剪辑、标准化和导出。转写与降噪先保留 provider 架子。

优点是最能体现产品差异，能证明它不是又一个音频编辑器。风险是同时涉及文稿、AI 和音频，工程面更宽。

### 备选：先做 AI 文稿准备工具

先不碰音频，只做播客文稿、资料区、AI 多任务和核查流程。

优点是开发更轻，能快速验证录音前准备需求。风险是产品容易变成普通 AI 写作工具，和播客的独特关系不够强。

### 备选：先做转写驱动的播客草剪工具

先不做复杂资料处理，只做导入音频、转写、文字删除、波纹剪辑和导出。

优点是音频价值明确。风险是会落入 Descript/剪映/专业剪辑工具的竞争框架，难以体现“创作准备”这条新流程。

## 6. MVP 范围

MVP 只追求一条最小闭环：

1. 创建一期节目项目。
2. 粘贴或编写基础大纲/文字稿。
3. 选中一段文稿，发起 AI 资料补充或事实核查任务。
4. 任务完成后，结果进入资料区，并能插入或引用到文稿。
5. 导入一段或多段录音音频到当前项目素材库。
6. 基于素材库资产生成代理音频和波形 peaks。
7. 通过时间线删除片段，默认波纹吸附。
8. 执行基础标准化。
9. 导出整体音频文件。
10. 保留转写和降噪的 provider 接口、配置入口和数据结构，但不要求第一阶段实现实际转写或降噪。

MVP 暂不要求：

- 内置云同步。
- 多人协作。
- 插件生态。
- 官方托管 AI 服务。
- 官方托管转写、资料检索或降噪服务。
- 账号体系和订阅计费。
- 专业混音、母带、自动配乐。
- 应用内录音。
- 实际转写能力。
- 在线转写服务。
- 实际降噪处理。
- 复杂工程模板。
- 移动端。
- 直接发布到播客平台。

## 7. 核心用户流程

### 7.1 创建项目

用户打开应用后创建一个节目项目。项目可以命名为一期节目的标题，也可以先使用临时标题。

项目创建后默认进入“准备”视图，展示文稿区、资料区和 AI/任务入口。

### 7.2 准备文稿

用户可以直接输入、粘贴或导入基础文字稿。文稿可以是完整逐字稿，也可以只是大纲。

文稿底层应是一份真实的 Markdown 文件，而不是只存在于数据库里的富文本对象。应用可以提供增强编辑体验，但正式内容层仍然是 `.md`：

- 正文保持普通 Markdown 可读。
- 资料引用可以使用自定义协议或自定义块语法，例如 `pa://source/S-04`、`pa-source`。
- 应用解析 Markdown 后生成段落、资料、引用和任务索引。
- 用户离开应用后，仍然可以用外部编辑器打开和阅读文稿。

系统需要把文稿切成可引用的段落单元。段落单元是 AI 任务、资料关联和后续录音提示的基础。段落 id 可以来自应用解析缓存，不强要求全部写入正文，但已经被引用或需要稳定追踪的段落必须能恢复映射。

### 7.3 发起 AI/agent 任务

用户选中一段文字，或把光标停在某个段落，然后向 AI 输入请求。

例子：

- “这里帮我找两个近三年的案例。”
- “这句话准确吗？帮我查一下。”
- “这段太口语化了，帮我整理成录音时更顺的表达。”
- “这里加一个背景解释，别太长。”

任务发起后进入任务列表。用户可以继续阅读文稿并发起新任务，不需要等待当前任务完成。

AI/agent 任务可以并行运行，但它们不能直接改写 Markdown。每个任务完成后先生成本地可见的结果和写入意图，用户采纳或系统允许自动采纳后，再进入统一写入队列。

### 7.4 处理任务结果

任务完成后，结果进入资料区，并保留来源和关联段落。

用户可以选择：

- 插入文稿。
- 作为旁注保留。
- 标记为已采纳。
- 忽略。
- 重新运行。
- 复制引用或来源。

任务结果默认先进入本地任务账本和资料候选区。只有被采纳的内容才写入正式 Markdown。这样 AI 可以大胆并行工作，但真正进入稿件的内容有清晰的落笔动作和追溯记录。

### 7.5 导入录音

用户完成录音后，把音频文件导入同一个项目。

MVP 需要保留产品的多轨方向，至少支持把多个音频素材放入不同轨道并参与整体导出。更细的轨道混音、轨道效果和复杂编组可以放到后续版本。

导入不是简单把音频文件交给前端播放器，也不是移动用户原始文件，而是进入本地素材库流程：

- 复制用户选择的音频文件到当前项目素材库。
- 保留原始路径、文件 hash、导入时间、文件大小等来源信息。
- 后续文档、转写和剪辑都引用素材库里的 `assetId`，不直接引用用户原始路径。
- 生成统一规格的代理音频，作为播放、转写和时间线预览的基础。
- 生成波形 peaks 数据，让时间线可以快速显示长音频。
- 把素材元信息、proxy 路径、peaks 路径写入项目索引。

素材库默认按项目隔离。检索和选择素材时默认只显示当前项目素材，但用户可以切换到跨项目搜索。跨项目使用素材时支持两种策略：

- 引用：当前项目引用另一个项目的 `LibraryAsset`。
- 复制：把素材复制到当前项目素材库，生成新的 `assetId`。

默认策略可以是引用，但需要给用户一个明确的“复制到当前项目”操作，避免无意识复制大音频。

MVP 只支持导入录音文件，不做应用内录音。应用内录音不进入当前阶段范围。

### 7.6 转写与文本剪辑预留

第一阶段可以先不做实际转写，只保留接口和数据结构。

预留能力包括：

- `TranscriptionProvider` 接口。
- 转写服务配置入口。
- 转写任务状态。
- 带时间戳的转写数据结构。
- 转写文本和时间线片段的映射结构。

后续实现时，可以选择本地 whisper.cpp，也可以选择在线服务。在线服务不是第一阶段必须能力。

当项目里已有转写结果时，用户可以通过文本定位音频片段；删除某段文本时，对应音频片段也被删除，时间线默认波纹吸附。没有转写结果时，用户仍然可以通过波形和时间线完成草剪。

静音段落、重复词、口癖和疑似口误候选都放到后续阶段。

转写模块的输入可以是素材库里的 `LibraryAsset`，也可以是当前 `AudioEditPlan`。前者对应“原始素材转写”，后者对应“当前剪辑版本转写”。转写结果不直接拥有音频文件，而是记录自己来源于哪个 asset 或 edit plan。

### 7.7 时间线草剪

用户也可以直接在时间线上做基础编辑：

- 多轨查看。
- 选择片段。
- 删除片段。
- 插入空白。
- 调整片段前后位置。
- 基础淡入淡出。
- 查看当前总时长。

默认行为是波纹剪辑。只有用户主动插入空白时，时间线上才出现空白段。

音频剪辑也是非破坏性编辑。用户在编辑器里修改的是 timeline edit plan / render plan，不是音频文件本身。删除、移动、增益、淡入淡出、标准化等操作都先变成计划数据，导出时再由本地音频引擎读取素材库资产和计划生成新音频。

### 7.8 导出

MVP 至少支持整体导出。

后续版本支持：

- 分轨导出。
- 导出剪辑决策列表。
- 导出转写文本。
- 导出给专业工具继续处理的中间格式。

## 8. 主要界面

### 8.1 项目首页

展示本地项目列表，包括标题、最近编辑时间、项目阶段、音频时长和是否有未完成任务。

### 8.2 准备视图

推荐布局：

- 左侧：AI 对话和任务列表。
- 中间：文稿编辑区。
- 右侧：资料补充区。

关键点是 AI 入口要能拿到当前可见上下文，资料区要和文稿段落建立关系。

### 8.3 任务中心

任务中心可以先作为左侧面板的一部分，不必做成独立页面。

每个任务至少展示：

- 任务标题或用户原始请求。
- 关联段落。
- 状态。
- 使用的模型或工具。
- 完成时间。
- 结果入口。

### 8.4 音频剪辑视图

推荐布局：

- 上方：导入音频、转写、标准化、导出等主要操作。
- 中间：多轨时间线和波形。
- 下方或侧边：转写文本区域，第一阶段可以是空状态或占位入口。
- 右侧：片段属性、标准化、淡入淡出等基础设置。降噪作为可配置能力预留。

如果第一版界面要更简单，可以先把转写文本放在时间线下方，降低多面板复杂度。

### 8.5 素材库视图

素材库视图用于管理当前项目和跨项目可引用的文件资产，和准备视图里的“资料补充区”不是同一个东西。

素材库至少展示：

- 当前项目音频素材。
- 素材来源、导入时间、文件大小、时长、hash。
- proxy、peaks、analysis 是否已生成。
- 素材被哪些文稿、转写、edit plan 引用。
- 跨项目素材搜索入口。

默认情况下，素材库只显示当前项目素材。用户需要主动切换范围，才显示其他项目或共享素材。跨项目素材可以直接引用，也可以复制到当前项目。

### 8.6 设置

设置需要覆盖：

- 本地工具链状态：FFmpeg、ffprobe、whisper.cpp、模型文件、后续可能的降噪工具。
- 本地工具路径配置：自动发现、手动选择 binary、重新检测、查看版本。
- Provider profile / base URL 配置：AI、资料检索、转写、降噪都通过 provider 接入。
- API key 管理：显示是否已配置，不在界面中长期展示明文。
- 开发者配置文件位置和当前生效配置说明。
- 转写服务选择：第一阶段可以只有接口和禁用态，但设置页需要解释为什么不可用，例如缺少 whisper.cpp、缺少模型文件、在线 provider 未配置。
- 依赖诊断：一键检查当前机器是否具备导入、proxy/peaks、导出、转写所需依赖。
- 本地项目存储位置。
- 素材库位置。
- 跨项目素材引用策略。
- 默认导出格式。
- 隐私和本地数据说明。

设置页的定位不是“偏好设置”，而是本地创作环境管理。由于产品不提供官方托管服务，也不默认打包所有外部工具，用户需要能清楚看到哪些能力已经可用、哪些能力只是预留接口、缺少什么依赖才能启用。

依赖状态至少分四种：

- 可用：路径存在，版本可读取，必要能力检查通过。
- 未配置：用户还没有选择 binary、模型文件或 provider profile。
- 不可用：配置了路径但文件不存在、无法执行或版本读取失败。
- 部分可用：例如 FFmpeg 可用但 ffprobe 缺失，或 whisper.cpp binary 可用但模型文件缺失。

## 9. 本地数据模型

本地数据模型需要体现产品的核心理念：正式内容、可重建缓存、持久暂存要分层。

```text
项目正式内容：
  episode.md
  library project assets

可重建缓存：
  document parse cache
  paragraph/source/link indexes
  audio proxy/peaks/analysis

持久暂存和账本：
  agent task ledger
  write intent journal
  document version snapshots
  audio edit plans
```

缓存层可以删除后重建；持久暂存层不能当普通缓存随便删，因为它负责崩溃恢复、写入解释和用户追溯。

推荐项目结构：

```text
workspace/
  workspace.json

  library/
    projects/
      ep-024/
        assets/
          audio/
            asset_a1_host_take.wav
            asset_a2_guest_take.wav
          attachments/
        assets.json
      ep-025/
        assets/
        assets.json
    shared/
      assets/
      assets.json

  projects/
    ep-024/
      project.json
      project.sqlite
      episode.md

      .podcast-artist/
        documents/
          episode/
            snapshot.json
            parsed-outline.json
            paragraph-map.json
            source-map.json
            link-map.json

        document-versions/
          episode/
            2026-06-02T21-12-08.123+08-00/
              episode.md
              meta.json

        tasks/
          task_xxx/
            task.json
            context.md
            result.md
            write-intent.json
            artifacts/

        write-journal/
          pending/
          applying/
          applied/
          failed/

        audio-cache/
          proxy/
          peaks/
          analysis/

        transcripts/
        edit-plans/
          rough-cut.plan.json
          export-master.plan.json
        renders/
```

`project.json` 是项目入口 manifest。`project.sqlite` 是可重建索引。`episode.md` 是当前正式文稿。`workspace/library/` 是素材库，按项目保存导入素材副本，也可以有 shared 区域。`.podcast-artist/documents/` 是解析缓存。`.podcast-artist/tasks/` 和 `.podcast-artist/write-journal/` 是任务账本和写入暂存层。`.podcast-artist/document-versions/` 保存文档旧版本快照。素材库资产不改写，音频编辑结果保存在 `edit-plans/`。

### Project

一期节目项目。

字段示例：

- id
- title

## 10. 技术方向

### 应用形态

- Electron 桌面应用。
- 前端负责主要交互，包括文稿、资料区、任务列表、转写文本和音频时间线。
- 主进程负责本地文件、音频处理调度、模型服务配置和安全边界。
- 音频重活交给本地音频引擎或本地任务执行，前端不负责完整解码长音频。

这里的关键边界是：Podcast Artist 是纯本地应用，只是使用前端技术构建界面。不要把它设计成“浏览器应用强行完整解码两小时音频”。正确分工是前端做交互，本地引擎做长音频处理。

### 本地存储

推荐使用“项目文件夹 + SQLite 索引”的方式：

- 素材库保存导入文件副本，按项目分子文件夹，也可有 shared 区域。
- Markdown 存正式文稿和已采纳资料。
- `.podcast-artist/` 存解析缓存、任务账本、写入队列、版本快照、音频计划和渲染记录。
- SQLite 存结构化索引和查询加速：项目、素材索引、段落索引、资料索引、任务状态、转写索引、时间线索引。
- 文档、转写和剪辑都通过 `assetId` 引用素材库资产。
- exports 目录存导出结果。
- project manifest 存项目基本信息和版本。

这种方式比单一大文件更容易备份和迁移，也比散落 JSON 更适合复杂查询。SQLite 不应该成为唯一真相来源；真正重要、需要恢复和解释的数据，要能在项目文件夹中被用户或开发者直接找到。

本地项目数据默认不做“为了隐藏内容”的加密或混淆。文稿、素材索引、任务账本、写入记录、版本快照和 edit plan 都应该尽量可读、可定位、可手动备份。需要保密处理的主要是 API key、访问 token 等凭证，它们应使用系统 keychain、Electron safeStorage 或等价机制单独保存，不进入项目文件夹的明文数据。

模块之间尽量通过 Markdown、JSON、清晰目录和稳定 id 协作，而不是通过复杂私有二进制或不可读大文件协作。这既能降低本地执行成本，也方便用户自己接入外部 agent 或脚本来辅助处理某个环节，例如批量整理资料、重跑转写、生成素材报告或检查 write journal。

### Markdown 文稿写入机制

文稿写入必须遵守：

- AI/agent 任务可以并行运行。
- 写入同一份 Markdown 必须串行。
- 任务完成后先生成本地可见的 `WriteIntent`。
- `WriteIntent` 进入统一写入队列，由主进程或本地写入服务处理。
- 写入前检查目标文档 hash；如外部编辑器修改过文件，走三方合并或提示用户。
- 写入前生成文档旧版本快照。
- 写入成功后标记 intent 为 `applied`，再更新 document cache。

写入队列状态建议：

```text
pending
  -> applying
  -> applied
  -> archived

pending
  -> applying
  -> failed
```

`pending`、`applying`、`failed` 不自动删除。`applied` 可以保留 30 天或最近 200 条。文档版本快照默认保留 30 天，过期后由本地维护任务清理。

### 文档版本快照

文档和音频不同：音频有不可变的素材库资产，文档没有单独的源文件层，`episode.md` 本身就是当前正式内容。因此每次改写 Markdown 前必须保存旧版本快照。

快照规则：

- 快照发生在写入前，不是写入后。
- 快照保存完整 Markdown，而不是只保存 diff。
- 快照记录触发原因、关联 taskId、关联 writeIntentId、旧 hash 和保留期限。
- 默认 30 天后清理。
- 用户可通过 UI 查看最近版本并恢复。

因为 Markdown 通常体积较小，即使频繁保存 30 天版本，空间成本也相对可控。

### AI/agent 接入

第一版可以先抽象出 Provider 层：

- OpenAI-compatible chat/completions 或 responses 接口。
- 自定义 base URL。
- 用户自带 API key。
- 开发者或用户配置 provider profile。
- 为未来 ACP、本地模型、本地工具执行留接口。

AI 调用时必须保存 contextSnapshot，避免任务完成后用户文稿已经变化而无法追溯。

产品不提供官方 AI/agent 服务。应用只负责读取配置、调度任务、保存上下文和结果；具体使用哪个模型、哪个转写服务、哪个资料检索服务，由 provider 配置决定。

因为项目数据尽量明文且模块边界清晰，外部 agent 可以直接读取项目文件夹中的 Markdown、任务账本、素材索引、转写结果和 edit plan。外部 agent 不一定要通过应用内 API 才能工作；应用需要做的是保证文件结构稳定、写入队列可恢复、冲突处理明确。

Provider 和本地工具链配置属于应用级或用户级配置，不属于单个项目的正式内容。项目可以记录自己使用过的 provider profile id、工具版本和导出参数，但 API key、机器上的 binary 绝对路径和本机模型目录不应该写入项目文件夹，避免迁移到另一台机器后产生误导。

### 音频处理

可拆成几层：

- 素材库资产保留，永不改写。
- 代理音频生成，可删除后重建。
- 波形 peaks 生成和播放控制，可删除后重建。
- 时间线剪辑决策保存为 edit plan / render plan。
- 转写结果和时间线映射，第一阶段先保留接口和数据结构。
- 局部预览缓存。
- 导出渲染。
- 标准化、淡入淡出等处理。
- 降噪 provider 预留。

早期可以优先保证剪辑决策可靠，不急着把所有音频处理都做成实时效果。

长音频性能目标依赖分层缓存：

- 时间线显示读取 peaks，不完整读取或解码整段音频。
- 播放预览优先使用 proxy 或局部 preview mix。
- 剪辑操作只修改 timeline edit plan，不立即改写音频文件。
- 最终导出由本地音频引擎根据素材库资产和 edit plan 重新渲染。

## 11. 关键体验要求

- 用户在阅读文稿时，可以低成本发起 AI 任务。
- AI 任务不会阻塞用户继续阅读、编辑和发起新任务。
- 任务结果必须能追溯到原始段落和来源。
- 任务结果、写入意图、写入结果必须在本地可追溯，应用意外关闭后不能丢失。
- 正式文稿是 Markdown 文件，用户可以在应用外打开和阅读。
- 写入正式文稿前必须生成旧版本快照。
- 添加音频或附件素材时，应用创建本地副本，不移动用户原始文件。
- 文档、转写和剪辑引用同一套素材库资产，默认检索当前项目素材，也支持跨项目引用。
- 删除音频片段后，默认不会留下空白。
- 素材库音频资产永不修改，所有剪辑操作都先写入 edit plan。
- 如果项目中有转写结果，转写文本和音频时间线必须互相定位。
- 长音频项目重新打开时，波形和时间线应能快速恢复，不需要每次重新分析原始音频。
- 前端界面在导入、转写、导出等本地重任务运行时仍然可操作。
- 导出结果要稳定可复现。
- 所有项目数据默认留在本地。
- 项目文件结构需要方便用户手动翻找、备份、迁移和排查问题。
- 除凭证外，项目数据不应默认以加密或混淆形式保存。
- 模块间数据格式应尽量明文、稳定、可被外部脚本或 agent 读取。

## 12. 错误和边界处理

### AI 任务失败

需要显示失败原因，并允许重试。失败不应影响文稿编辑和其他任务。

### 文稿变化

如果任务运行期间关联段落被修改或删除，任务结果仍保留原始 contextSnapshot，并提示用户结果基于旧版本上下文。

### 外部编辑器修改 Markdown

如果用户用外部编辑器修改了当前 Markdown，应用写入前必须检测 hash 变化。可自动三方合并时自动合并；无法合并时提示用户处理冲突，不能静默覆盖。

### 应用意外关闭

应用重启后需要扫描本地任务账本和写入队列：

- `pending` 恢复为待处理。
- `applying` 需要校验是否已经写入成功；无法确认时进入人工确认或 failed。
- `failed` 保留错误原因和重试入口。
- 已生成但未采纳的任务结果仍留在资料候选区或任务记录中。

### 音频文件移动或缺失

项目打开时如果发现素材库副本缺失，需要提示用户重新定位或重新导入文件，不能静默失败。用户原始导入路径只作为来源信息和辅助定位，不作为运行时强依赖。

### 转写失败

第一阶段没有实际转写时，转写入口应显示为未配置或暂不可用。后续接入转写 provider 后，转写失败仍允许用户进行波形剪辑，并允许重试或更换 provider。

### 导出失败

导出失败需要保留剪辑决策，不影响项目本身。错误信息要能说明是文件权限、编码失败还是素材缺失。

### 本地依赖缺失

如果 FFmpeg、ffprobe、whisper.cpp 或模型文件缺失，应用不能在用户执行到一半时才给出含糊错误。设置页需要提前显示依赖状态；相关功能入口也要显示未配置或不可用原因。例如 FFmpeg 不可用时，proxy/peaks 生成、标准化和导出应提示用户先完成本地工具链配置。

### 缓存清理

可重建缓存可以清理，例如 document parse cache、proxy、peaks、analysis、preview mix。持久暂存不能按普通缓存处理：

- `pending`、`applying`、`failed` write intent 不自动清理。
- 文档版本快照默认保留 30 天。
- 已应用 write journal 可保留 30 天或最近 200 条。
- 素材库音频资产和 edit plan 不自动清理。

## 13. 验收标准

MVP 达到可用状态时，应满足：

- 可以创建并重新打开本地项目。
- 可以在设置页看到 FFmpeg、ffprobe、whisper.cpp、模型文件和 provider profiles 的配置状态。
- FFmpeg/ffprobe 可用性检查通过后，才允许执行依赖它们的 proxy、peaks、标准化和导出流程。
- 文稿底层是 Markdown 文件，应用外可以打开阅读。
- 可以编辑文稿，并按段落发起至少两条并行 AI 任务。
- 任务结果可以进入资料区，并与段落建立关系。
- 任务结果先进入本地任务账本；采纳后生成 write intent 并串行写入 Markdown。
- 每次写入 Markdown 前会生成 30 天保留的旧版本快照。
- 应用关闭后重新打开，pending/failed write intent 和任务结果仍然可见。
- 可以导入至少一个音频文件。
- 导入音频时会复制到当前项目素材库，并生成 `LibraryAsset`。
- 用户原始路径不会被移动或修改。
- 文档、转写和 edit plan 通过 `assetId` 引用音频素材。
- 素材库默认只显示当前项目素材；数据结构支持跨项目引用。
- 可以生成代理音频和波形 peaks。
- 可以通过时间线删除音频片段。
- 删除后时间线自动波纹吸附。
- 音频剪辑结果保存在 edit plan，导出时根据素材库资产和 plan 生成新文件。
- 可以执行基础标准化并整体导出音频。
- 转写和降噪有 provider 接口、配置入口和数据结构占位，但不要求实际执行。
- 关闭应用后重新打开，文稿、任务、资料、音频素材和剪辑决策仍然存在。

## 15. 未定问题

- AI 对话固定在左侧，还是做成可收起的任务抽屉？
- 资料区是否必须强绑定段落，还是允许一个独立资料库？
- 任务结果最终应该更像资料卡片、聊天消息，还是任务单？
- “单入单出”目前先按淡入淡出理解；如果实际指单声道输入输出或别的处理，需要修正。
- MVP 的多轨支持做到什么颗粒度：仅导入、排列和整体导出，还是要支持轨道级音量、静音、独听和分轨导出？
- 转写时间戳是否足够细，尤其是 whisper.cpp 输出能否满足文本剪辑精度要求？
- 项目文件夹结构是否需要支持打包成单文件方便分享？

## 16. 下一步建议

下一步可以继续拆三份更具体的设计：

1. `准备视图交互设计`：文稿、资料区、AI 任务怎么协作。
2. `音频草剪交互设计`：导入、proxy/peaks、时间线、波纹剪辑、转写占位怎么协作。
3. `本地项目数据设计`：SQLite schema、文件夹结构、迁移策略。

其中最值得先拆的是准备视图，因为它决定这个产品和普通音频剪辑器的差异。
